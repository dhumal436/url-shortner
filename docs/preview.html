ShortLink Engineering Documentation

A deliberately evolving URL-shortener platform used to learn modern .NET and system design: API design, relational modeling, caching, concurrency, asynchronous processing, observability, load testing, and horizontal scaling.

Start simpleModular monolith + PostgreSQL before distributed complexity.
Measure firstAdd Redis, queues, replicas, and other components because a real constraint justifies them.
Document decisionsEvery meaningful architecture choice gets an ADR with trade-offs.

How to use this documentation

Build the system in stages. Revisit the architecture after each stage, capture what changed, and record the reasoning. The goal is not to manufacture a giant diagram on day one. The goal is to understand why each piece exists.

Database learning topics

Normalization, unique constraints, composite indexes, query plans, transactions, isolation levels, connection pooling, and EXPLAIN ANALYZE should all be practiced directly.

Concurrency

For custom aliases, combine application-level validation with a database UNIQUE(Code) constraint and handle duplicate-key failures cleanly. This protects correctness even when two or more API instances receive the same alias concurrently.

Asynchronous work

Analytics should not make the user-facing redirect depend on a slow analytics database. Publish an event and process it asynchronously so the critical path stays small.

ADR-001: Modular Monolith

Decision Proposed

Problem: We need an architecture that supports production-grade structure without creating distributed-system complexity before it is necessary.

Decision: Start as a modular monolith with Api, Application, Domain, and Infrastructure projects.

Why: Fast development, simple deployment, clear dependency boundaries, and an easier path to learning fundamentals.

Trade-offs: Less independent scaling than microservices, but substantially lower operational complexity.

ADR-002: PostgreSQL

Decision Proposed

Problem: We need durable storage with strong constraints, transactions, indexing, and mature tooling.

Decision: Use PostgreSQL for the primary relational store.

Trade-offs: Excellent consistency and query capabilities, with operational considerations for scaling very large workloads.

ADR-003: Short Code Generation

Decision Proposed

Problem: Short URLs need compact, unique codes that remain practical under concurrency.

Options: Random Base62, database ID to Base62, or a distributed ID generator.

Decision: Start with a simple approach and benchmark/measure collision behavior before introducing distributed ID infrastructure.

Key questions: Code length, collision probability, retry policy, predictability, and whether sequence growth should be externally visible.

ADR-004: Redis

Decision Proposed

Problem: Redirect traffic is much more read-heavy than link creation traffic.

Decision: Add Redis as a distributed cache for link resolution.

Pattern: Cache-aside with TTL and explicit invalidation when link state changes.

Trade-offs: Lower latency and lower database load at the cost of cache invalidation and another operational dependency.

ADR-005: Asynchronous Analytics

Decision Proposed

Problem: Synchronous analytics writes can increase redirect latency and couple the critical path to analytics storage availability.

Decision: Emit click events asynchronously and process them with a worker.

Trade-offs: Analytics become eventually consistent, but redirect availability and latency are better isolated from analytics failures.

ADR-006: Unique Code Concurrency

Decision Proposed

Problem: Multiple concurrent requests may attempt to create the same custom alias.

Decision: Enforce uniqueness in PostgreSQL and handle duplicate-key errors in the application.

Trade-offs: The database becomes the final correctness boundary, avoiding race conditions inherent in check-then-insert logic.

ADR-007: Rate Limiting

Decision Proposed

Problem: Public endpoints can be abused for spam, brute force, or resource exhaustion.

Decision: Use endpoint-appropriate rate limits, initially partitioned by user and/or IP.

Example policies: Link creation 10/minute/user; login 5/minute/IP; redirect access governed by a higher threshold and abuse controls.

Trade-offs: Better abuse resistance, but limits must be load-tested to avoid blocking legitimate traffic.

ADR-008: Outbox Pattern

Decision Proposed

Problem: A database transaction can succeed while publishing an event fails, leaving the system inconsistent.

Decision: Store the business change and an outbox message in the same database transaction, then publish the message asynchronously.

Trade-offs: More reliable event publication with added storage and worker complexity.

Engineering Principles

Build the same path multiple times.
Compare API → DB, then API → Redis → DB, then multiple API instances, then asynchronous analytics. Measure latency, throughput, failure modes, consistency, cost, and operational complexity.
Every new component needs a reason.
Architecture is not a shopping list of technologies. The system should make the pressure visible first.
Document trade-offs, not just decisions.
The useful question in system design is rarely “What did we pick?” It is “What problem were we solving, what alternatives existed, and what did we give up?”
